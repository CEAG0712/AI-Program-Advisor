## C–D. HTTP contract and runtime validation

`POST /recommendations` requires the existing bearer credential and `Content-Type: application/json`, optionally `; charset=utf-8`. Example:

```json
{"budget_cents":30000,"weekly_hours":6,"known_skills":["basic-python"]}
```

The only accepted keys are those three required keys. Budget is a JSON number, safe integer, 0–100000000 USD cents. Weekly hours is a number, integer, 1–168. No coercion from strings, booleans or null; fractional/non-finite values fail. JSON cannot encode NaN/Infinity directly; unit tests exercise those values and HTTP tests exercise overflow and malformed JSON.

Skills must be an array of 0–32 unique strings, each 1–64 characters with lowercase letters/digits separated by single hyphens. Case variants, whitespace (including trailing newlines), empty segments, objects, nested arrays and duplicates fail. A present empty list explicitly declares no skills; a missing list is invalid. Validation creates a detached frozen request/list. It does not infer or silently normalize related skills.

Unknown keys, including `tenant_id`, `academy_id`, `eligibility_override`, `checkout_authorized` and model instructions, fail with 400. Validated input is not authorization. TypeScript interfaces disappear at runtime; incoming JSON starts as `unknown` and must pass executable checks.

Success is HTTP 200 with `{"recommendations":[...]}`. Each item contains exactly stored `offer_id`, `title`, `price_cents`, `currency`, `required_skills`, `weekly_study_hours`, plus three fixed reasons. Valid no-match is HTTP 200 with `{"recommendations":[]}`. Input/parser errors are fixed 400; authentication errors keep existing fixed 401; catalog failure/overflow is fixed 503. Recommendation middleware sets no-store before parsing, including tested 400/401/503 responses.

The existing parser bounds JSON to 100 KiB. A catch-all filter is registered through APP_FILTER because parser errors occur before controller dispatch. It normalizes only recommendation-path parser/input 400/413/415 statuses to the fixed 400 body; other paths/errors delegate to Nest's existing filter. This handles raw body-parser errors as well as Nest exceptions without logging raw parser details. Parsing can reject a malformed body before authentication executes. No new logging of learner bodies or credentials was added.

## E–I. Authorization, catalog, policy and ranking

Request flow: shared `DemoAuthGuard` verifies the credential and maps it to a server-controlled academy; the private request symbol carries that context through `AuthenticatedTenant`; controller validates the body; service requests bounded candidates from `CatalogRepository`; pure policy returns the response. Caller query/header values cannot replace the trusted context. Body tenant/authority fields are rejected.

The new repository method reuses `CATALOG_SQL`: explicit factual fields, `WHERE tenant_id = $1 AND active = TRUE ORDER BY offer_id ASC`. Tenant comes only from the authenticated context. It adds parameterized `LIMIT $2` with 1001. At most 1000 active rows are supported. A sentinel 1001st row causes a sanitized 503 refusal; no partial-page ranking or global-optimum claim. The candidate bound applies before eligibility filtering. The original `/catalog/offers` method remains unchanged.

USD is the only request denomination; non-USD rows are excluded rather than compared as if currencies were equivalent. Budget/time use inclusive comparisons. Every stored required skill must appear exactly in the declared set. No prerequisite labels means that check passes. `python` does not imply `basic-python`; `basic-python` does not imply SQL.

Only suitable authorized active candidates enter ranking. Comparator:

```text
weekly_study_hours descending
then price_cents ascending
then offer_id ascending by JavaScript code-unit comparison
```

This capacity-use preference is transparent, deterministic and not a learned suitability score. Filtering creates a new array; sorting does not mutate database rows/input ordering. Output skill/reason arrays are detached. Apply the maximum of ten only after filtering and sorting. Unique SQL primary-key IDs provide the explicit final tie-breaker. No randomness, clock or model participates.

Reasons are exactly “Within the declared budget.”, “Fits the weekly study-hour limit.” and “Required skills match the declared skills.” They describe the policy checks only. No testimonials, outcomes, guarantees or verified competence claims. Suitability under self-declared skill labels is not formal credential verification, academy admission, enrollment, course reservation, availability guarantee or checkout permission. PostgreSQL owns synthetic facts at query time; later purchase terms require a separate revalidation boundary. Provider ingestion is still a future architectural boundary.

## S. Senior/Staff CHEAT MODE: full model answers and adversarial defenses

### 1. Tenant spoofing through recommendations

The request cannot choose tenant authority. The existing guard resolves a verified bearer credential into a fixed server mapping and attaches a module-private symbol; the decorator retrieves it, and repository SQL binds that value to the tenant predicate. Query/header academy names are unused; body authority fields fail the exact-key validator. Real HTTP tests exercise both directions and compare complete persisted collections.

Why alternatives fail: accepting a request tenant ID and merely parameterizing it prevents SQL injection but still allows unauthorized tenant selection. Comparing a response tenant label after an unscoped read leaks data too late. Follow-up: trusted code can still forge the structural context or omit a predicate, so every future entry point needs the same security review; this is not proof against process compromise.

### 2. Missing versus declared prerequisites

Missing `known_skills` is invalid. An explicit empty list states no known skills. The policy requires each stored prerequisite to be a member of the exact declared set; no related-skill inference occurs. Offers without prerequisite labels pass that check only. Filtering precedes ranking.

Why alternatives fail: defaulting missing skills to “all skills” converts uncertainty into permission; fuzzy Python/SQL similarity invents expertise. Follow-up: the caller can lie about declared skills. That does not change the contract into verified expertise; admission requires separately trusted evidence and policy.

### 3. Declared skills versus admission eligibility

The endpoint computes suitability under synthetic self-declared labels. Fixed reasons say required labels match declarations. There is no credential verification, competency assessment, academy-specific admission approval or enrollment. The distinction is documented in code, README and this record.

Why alternatives fail: calling a matched string “verified skill” launders a user assertion into authority. Follow-up: if an academy later demands verified prerequisites, add an independently authorized evidence/verification workflow and a fail-closed admission gate; do not rename this response into proof.

### 4. Price authority and stale facts

The response copies integer cents/currency from the authorized PostgreSQL query, not caller/model proposals. Budget is USD and other currencies are excluded. Current reads are snapshots, not future purchase quotes. A later checkout must re-read price, ownership, prerequisites and availability and bind explicit confirmation to current terms under a chosen concurrency policy.

Why alternatives fail: cached/model prices or unversioned recommendation-as-quote can be stale or invented. Follow-up: a single SELECT is internally consistent for that statement but provides no reservation. Quote expiry, provider reconciliation, locking/version policy and currency conversion remain future design work.

### 5. Determinism and changing ranking policy

The comparator is hours descending, cents ascending, code-unit ID ascending, applied after eligibility, capped at ten. It avoids locale-dependent string sorting, random values and clocks. Unit tests reverse/shuffle rows and check all tie-breaks; real requests repeat exact order. The policy prefers using declared study capacity, not measured learning success.

Why alternatives fail: sorting before exclusion can promote unsuitable offers; relying on input order leaves ties sensitive to retrieval. Follow-up: changing policy should be an explicit reviewed/versioned decision with updated golden expectations and evaluation, not a covert comparator tweak. Catalog/input changes can legitimately change output without violating determinism for identical inputs and facts.

### 6. Unexpectedly large tenant catalog

The bounded SQL query fetches at most 1001 rows. More than 1000 causes fixed 503 refusal before policy evaluation. At or below 1000 all active tenant candidates are considered; ten is an output cap, not an arbitrary candidate page. Unit tests cover exactly 1000, overflow, parameters and failure behavior.

Why alternatives fail: ranking only the first page while implying full-catalog suitability is incomplete; unbounded retrieval risks memory growth. Follow-up: LIMIT bounds materialized rows, not scan cost or text-array sizes. Larger workloads need separately designed tenant indexing, server-side eligibility/ranking, pagination/completeness semantics and measured resource limits. The current fixtures were not expanded to simulate production scale.

### 7. Database outage versus zero-match

A successful read may filter to an empty list, returning 200. A failed read returns 503, never an empty result. A real closed-port connection tests this separation. Process health remains 200 because it describes the process, not dependency readiness.

Why alternatives fail: catch-and-return-empty hides outages as business outcomes; retry storms multiply pressure. Follow-up: this fault test does not establish failover or an SLO. Symptoms → 503 increase; evidence → sanitized dependency metrics and scoped connectivity/identity checks; isolation → distinguish process health from SQL access; diagnosis → connection/timeout/session condition; containment → bounded failure, no invented offers; durable correction → fix verified dependency cause under separate authorization; recovery verification → real scoped SQL plus HTTP and negative tests; blast radius → identify affected time/tenant requests without logging full learner bodies. RTO/RPO are unresolved.

### 8. Shared database role without RLS

Tenant isolation is application-enforced. The existing bootstrap role is superuser/owner and can read all tenant rows; tests prove specific request paths, not database-enforced isolation or safety after process compromise. Parameterized SQL is necessary but not sufficient.

Why alternatives fail: claiming RLS because a query has a tenant WHERE clause confuses separate controls. Adding RLS while retaining a bypassing superuser may create false confidence. Follow-up: least-privilege runtime roles, forced/tested policies where appropriate and transaction-local tenant context require a separately scoped design and migration. This increment cannot claim those protections or alter schema/roles.

### 9. Future LLM eligibility override

No LLM is called here. Future model tool requests must remain untrusted input to the same backend validation/authentication/policy. Models may suggest learner intent, never authorize tenant, waive prerequisites, establish price or approve checkout. Unknown keys currently reject override attempts.

Why alternatives fail: prompt instructions alone are probabilistic and can be bypassed; accepting a model boolean as policy permission relocates authority to untrusted output. Follow-up: future orchestration should use bounded approved tool contracts and revalidate tool results/response membership. Unknown skill evidence remains unknown; a conversational claim is not verified admission evidence.

### 10. Malicious instructions in course text

Titles are database facts, treated as inert strings and serialized into JSON. They are not parsed as commands, policies or tool calls. There is no model/browser execution in this implementation. A future UI must escape output; a future model must receive catalog strings as untrusted data and lack authority to convert their text into policy.

Why alternatives fail: a trusted database location does not make text safe as instructions; filtering words like “ignore” cannot establish a security boundary. Follow-up: future model use needs structural separation, constrained tool authority and adversarial fixtures; HTML/Markdown consumers need context-specific escaping. Current inert JSON serialization does not prove those future consumers safe.

### 11. Recommendation mistaken for checkout permission

Recovery verification → complete real HTTP/SQL tenant matrix, cache checks if applicable, full source audit and approved redeployment only when separately authorized. Blast radius → identify affected tenants, records, time range and consumers from trustworthy evidence, with human-led notification decisions.

Why alternatives fail: filtering foreign rows only at display time may leave logs/caches exposed; deleting evidence prevents impact analysis. Follow-up: current tests cannot guarantee zero undiscovered exposure or retroactively retract data. No breach response or deployment action occurred here; RTO/RPO and legal/operational obligations are not invented.

### 13. Fixture corruption during integration

Containment → stop further fixture-mutating verification and report blocked/partial evidence; never reset or remove the volume to hide corruption. Recovery verification → compare all fields, rerun isolated serial real SQL/HTTP acceptance, verify restoration again. Blast radius → determine whether only disposable fixtures or unrelated data were touched, rather than assuming IDs prove isolation.

Why alternatives fail: reseeding with overwrite may conceal damage; comparing only six IDs misses price/skills/activity corruption. Follow-up: the new suite is read-only, but unchanged D1.2 has a crash window during activity mutation. Outer and inner snapshots reduce unnoticed corruption; they cannot guarantee recovery after a killed process. RTO/RPO remain unresolved.

### 14. Cleanup failure masking the original failure

The cleanup helper catches the body failure, then independently attempts every cleanup; one error is rethrown, multiple errors become AggregateError preserving each original error. Snapshot verification is itself a cleanup step; its failure cannot skip application/pool closure. A regression deliberately throws during body/cleanup and checks that later cleanup still ran. Optional resource references support setup failure before initialization.

Why alternatives fail: a single `finally` containing sequential awaited closures skips later operations when the first throws; throwing a new generic error discards the original diagnostic. Follow-up: errors are retained for trusted test diagnostics, not exposed through application HTTP. A forcibly killed process can still bypass JavaScript cleanup; this does not establish crash-safe resource recovery or fixture transactions.
