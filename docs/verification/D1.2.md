## G–H. HTTP, authentication and isolation

`GET /health` returns 200 `{ "status": "ok" }`, with no dependency details. `GET /catalog/offers` requires a demo bearer credential and returns a deterministic array of offer facts. Missing, malformed or invalid credentials return a fixed 401 JSON body. Valid empty scope returns 200 `[]`. Failed database access returns a fixed 503 JSON body, never a successful fabricated collection.

The [guard](../../src/catalog/demo-auth.guard.ts) checks token syntax/length, compares fixed-size SHA-256 digests using `timingSafeEqual` for both configured credentials, and maps the matching credential to a fixed academy. This reduces comparison leakage; it is not a claim that complete HTTP execution has constant timing. The [request symbol](../../src/catalog/tenant-context.ts) cannot be created by serialized client headers/query values. The controller reads only that authenticated context, and the service carries it unchanged into the [repository](../../src/catalog/catalog.repository.ts):

```sql
SELECT offer_id, title, price_cents, currency, required_skills, weekly_study_hours
FROM course_offers
WHERE tenant_id = $1 AND active = TRUE
ORDER BY offer_id ASC
```

`$1` is a separate bound parameter derived from the verified context. Client tenant inputs have no path into it. There is no model, ranker or checkout authority. Successful catalog responses carry `Cache-Control: no-store`; there is no shared application cache.

Actual negative checks: A credential plus B query parameters; A credential plus B values in `x-tenant-id`, `tenant-id` and `tenant_id` headers; B credential plus A query/header; missing token; wrong token; Basic scheme; duplicated/comma-joined credentials; malformed Bearer. Spoofing returned only the authenticated academy's full expected collection, and authentication failures returned 401. Full-body equality detects foreign IDs, titles, prices and prerequisite metadata, not merely an echoed tenant label. Response checks also assert actual demo secrets and database password are absent. Unit tests reject oversized inputs and check safe SQL-error mapping.

For a real empty catalog, integration temporarily deactivated only B's two active fixtures, verified B 200 `[]` and A unaffected, then restored B and checked the entire original database snapshot. Failure simulation used a second actual Nest application pointed at a just-closed ephemeral localhost TCP port: real driver connection refusal yielded 503, its process health remained 200, and the original PostgreSQL-backed application remained available. No database daemon was stopped and no unrelated service was touched.

## N. Senior/Staff CHEAT MODE defense

**1. Where is the actual authorization boundary, and can the branded-looking TypeScript context prove it?**

The boundary is `DemoAuthGuard.canActivate`: only a valid configured bearer credential produces a fixed tenant mapping, stored under a module-private request symbol. The controller retrieves that symbol; serialized tenant headers/query inputs are ignored. The repository binds the tenant into SQL. The `TenantContext` interface is structurally typed, not an unforgeable capability; trusted application code can manufacture it. Runtime protection therefore depends on the guard/decorator/request path, not compile-time branding. Bidirectional full-body spoofing tests exercise that path through real HTTP and SQL.

Follow-up defense: application compromise or a newly added unguarded controller is outside this proof. A production extension would require explicit authentication policy, least-privilege database roles, carefully configured RLS if chosen, and reviews/tests for every new path. RLS is not implemented here and the bootstrap superuser would undermine a naive RLS claim.

**2. Why does parameterized SQL not establish tenant isolation by itself?**

Parameters prevent treating the bound tenant string as executable SQL, but they do not establish who may choose that string or guarantee a tenant predicate exists. Here three independent conditions matter: verified credential mapping, preserved server-side context, and `WHERE tenant_id = $1 AND active = TRUE`. The unit test checks parameter propagation; real integration proves both tenants and spoofed inputs yield the exact authorized persisted collection. Neither a parameter placeholder nor a returned tenant label alone proves the full property.

Follow-up defense: the tests are finite evidence, not universal proof. A future offer-ID lookup, background job or cache must preserve authorization independently. This implementation has no cache and marks successful responses no-store; it cannot certify future paths.

**3. Distinguish no inventory from database failure under partial failure and explain the timeout bounds.**

A successful query returns its rows, including zero rows. A query rejection throws a fixed `ServiceUnavailableException`; it never becomes `[]`. The pool limits connections to four; connection acquisition and client query waits are bounded at two seconds and server statement execution at 1.5 seconds. Idle pool errors are handled without raw error details. The real closed-port test confirms a connection attempt can fail safely while process health remains 200.

Follow-up defense: the configured limits do not prove an end-to-end SLO or cancellation behavior under every partition. Query timeout alone need not stop server execution; statement timeout provides a separate server bound once connected. This suite does not measure overload, operating-system failures or in-flight connection loss. Production dependency telemetry, backpressure and fault tests require a separately scoped increment.

**4. Can this API guarantee authoritative prices and eligibility at checkout?**

It guarantees only that the tested catalog response copies integer cents/currency from the authenticated tenant's current PostgreSQL rows. Integration checks full responses against direct SQL and fixed fixture prices. It neither accepts model prices nor calls a model. Active offers and prerequisite metadata do not establish a particular learner's eligibility. There is no checkout endpoint or transaction/reservation guarantee.
